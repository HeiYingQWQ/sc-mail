## 1. 产品目标

用户负责维护业务关系，系统负责保存邮件、匹配已登记邮箱，并通过内置 AI 判断项目归属、生成有来源的进度总结。

- **联系人**：由用户主动添加；添加后即可查看与其已登记邮箱的历史和后续收发邮件。
- **公司**：由用户创建，选择一个或多个已有联系人，并手动填写官网、地址、备注等资料。
- **项目**：由用户创建，选择所属公司和项目对接联系人；同一公司可以有多个独立项目。
- **项目详情**：显示项目资料、对接人、属于这个项目的邮件往来、对话总结、阶段、待办与等待事项。
- **分析邮件**：用户发起历史分析；后续新邮件按已设置的项目联系人自动分析。清楚属于已有项目的邮件自动归类，无法确定的邮件留待检查。
- **项目通知**：进行中项目收到相关真人新来信，产生可恢复的 OpenClaw 通知事件；历史分析和已结束项目不触发此类通知。

例如，同一公司有“德国展会项目”和“美国展会项目”，两者可以使用同一位对接人，但邮件、摘要和进度分别管理。

## 3. 联系人管理

### 3.1 创建和维护

联系人不再由同步、分类、模型分析、Agent 事件处理或对账自动创建，也不生成“发现新发件人，等待确认联系人”的常规流程。

用户可通过 Dashboard 添加联系人；API/CLI/MCP 的创建入口只能执行用户明确发起的创建操作，工具可用不代表 Agent 可以自行扩充通讯录。收到邮件的地址仍保存在原始邮件及地址字段中，并正常同步、分类和查询。

目标字段：

| 字段 | 规则 |
| --- | --- |
| 姓名/显示名称 | 用户填写，必填 |
| 邮箱 | 至少一个，支持添加多个已知邮箱及选择主邮箱 |
| 所属公司 | 可不设置；设置或更换由用户操作 |
| 备注 | 用户填写，可选 |

手动保存后联系人直接可用，不再要求确认“系统猜测的身份”。邮箱按项目统一规则规范化和精确匹配；不按相似姓名、签名或同域名合并。一个邮箱不得同时绑定两个有效联系人，冲突提示现有记录，不静默覆盖。

### 3.2 添加后查看往来

- 点击联系人，显示其资料和所有已登记邮箱的邮件往来；包含已同步的历史邮件及后续新邮件。
- 来信按 From 匹配，发件按 To/CC/BCC 匹配；联系人出现在 CC 的邮件可显示，但明确其参与方式，不当作其直接发信或已回复。
- 一个邮件可以涉及多位已登记联系人；列表不能只依赖当前单一 EmailMessage.contactId 而漏掉其他参与人。
- 同一联系人有多个邮箱时合并展示，保留实际地址、方向、主题、时间、项目归属和来源。文件夹副本按账号与 RFC Message-ID 合并逻辑展示，原始证据不删除。
- 支持分页及日期/项目筛选。无邮件显示空状态，不能为填充界面创建合成事实。
- 添加联系人后的历史匹配只建立或查询关系，不重发旧通知、不自动改分类、不自动创建任务。

“所有往来”仅指 Ai Mail 已同步的受管文件夹；无 IMAP 副本的外部群发仍不可见。页面如实显示同步范围和数据新鲜度。

## 4. 公司管理

### 4.1 手动资料与成员

用户创建公司并选择一个或多个联系人。公司是独立业务实体，不以邮件域名相同作为创建或归属依据。

| 字段 | 规则 |
| --- | --- |
| 公司名称 | 用户填写，必填 |
| 官网 | 用户填写，可选；校验 http/https 地址，安全打开，不自动抓取网站 |
| 地址 | 用户填写，可选；支持实际业务地址文本 |
| 备注 | 用户填写，可选 |
| 联系人 | 从已有联系人中多选，可维护成员 |
| 域名 | 原有兼容字段可保留为资料，不承担自动归属规则 |

联系人姓名、公司名称、官网、地址和备注均不从邮件签名、域名或模型结果自动写入。共享 Gmail/Outlook 地址或不同域名的联系人也可以由用户加入同一公司。

### 4.2 公司详情

点击公司后应显示：公司资料与编辑入口、联系人列表、该公司的项目列表。点击成员可进入联系人详情；点击项目可进入项目详情。

允许添加、移除或调整联系人关系。联系人从公司移除不删除该联系人、邮件或历史业务证据；已有项目中的对接关系须显式提示并由用户处理，不能悄悄迁移项目或删除来源。

公司汇总邮件若展示，应注明是公司成员的往来汇总，并保留项目标签；不能据此将这些邮件分配给公司的每个项目。

## 5. 项目管理

### 5.1 创建及关系

用户创建项目时填写项目名称、选择一个所属公司，并从该公司的联系人中选择一个或多个对接人。一个联系人可以参与同一公司的多个项目。

| 内容 | 目标 |
| --- | --- |
| 项目名称 | 必填，如“德国展会项目”“美国展会项目” |
| 所属公司 | 新流程必选已有公司；保留旧无公司项目供用户整理 |
| 对接联系人 | 多选；可标记主对接人，不能凭邮件自动添加成员 |
| 说明/备注 | 用户填写，可选 |
| 展会、国家/地点、日期 | 用于区分项目的可选资料；准确字段在实施时确定，不把示例变成必填项 |
| 阶段 | 复用现有阶段规则，用户可维护 |
| 项目状态 | `status` 为 `active|completed`；`stage=completed` 当且仅当状态 `completed`，状态变更时 PATCH 提交一致的最终组合 |

公司新增其他联系人不会自动把其加入现有项目。更换公司须一并校验所选对接人；原有关系有冲突时返回明确提示，不保留无效组合。移除项目联系人不删除已归属项目的历史邮件，只影响后续候选匹配和当前成员展示。

状态由用户修改，AI 不自动结束、重开或创建项目。“已结束”项目保留邮件和资料，也作为归属判断的候选，避免旧项目后续邮件被塞入新的进行中项目。已有阶段中的 completed 与项目状态须统一转换规则，不能同时显示“阶段已完成、状态进行中”而不解释其含义。

### 5.2 项目详情

- **项目资料**：名称、所属公司、说明/备注、状态、当前阶段与可选展会信息。
- **对接人**：项目所选联系人、主对接人、已登记邮箱，可查看其详情。
- **邮件往来**：已归属本项目的收发邮件，按时间查看，支持分页和联系人筛选。
- **对话总结**：本项目最新可用摘要，附更新时间、来源和覆盖范围；没有摘要或摘要落后于邮件时如实说明。
- **进展**：阶段、开放待办、待回复/等待方、期限以及时间线。无可靠依据时不展示臆造的完成百分比。
- **分析入口**：“分析邮件”按钮、分析范围、任务进度、已处理/失败/待确认数量及最近分析时间；允许查看归类依据并修正。

沿用现有任务证据、人工覆盖、摘要版本和过期输入保护。发出邮件不自动完成项目；自动回执不推进项目进度。分类可以比较多个候选项目，但项目总结只使用本项目已归属邮件，不能将其他项目的往来纳入。

## 6. AI 归类、总结与新来信通知

**联系人关系证明“和谁往来”，项目归属证明“这次往来讨论哪件事”；两者不能互相替代。**

### 6.1 点击“分析邮件”

1. 用户创建项目，设置公司、对接人和可用的项目说明，点击“分析邮件”。
2. 页面展示候选邮件数量及日期范围；默认围绕项目时间范围检索，允许扩大范围。没有项目日期时采用明确可见的范围，不默默分析所有年份。
3. 从项目联系人的已登记邮箱查找已同步的收发邮件，按账号和邮件身份去重，并带入相关回复上下文。检索范围和实际完成范围要能查看。
4. 向内置 AI 提供候选邮件、该联系人关联的进行中及已结束项目、必要的公司/项目资料和已有人工归属。不能只提供当前项目并强迫模型二选一。
5. AI 输出每封邮件的归属判断及来源证据；业务服务校验后，明确且无冲突的结果自动归类，不确定的留待检查，人工归属保持优先。
6. 基于已确认属于本项目的邮件生成进度总结，保存新的派生摘要版本，并显示来源、覆盖范围和更新时间。

批量分析作为后台任务执行，页面显示进度，允许取消尚未执行的部分、重试失败项。已成功处理的邮件不重复写入。只分析联系人往来不等于修改通讯录，不允许模型新增联系人、公司、项目或对接人。

### 6.2 项目判断规则

联系人匹配只确定候选范围。即使只有一个项目，也要先判断邮件是否与该项目有关；问候、私事和下一轮新合作不能全部归进去。单项目可以简化候选选择，不能省掉内容判断。

判断综合使用当前正文、主题、真实回复关系、展会/地点/日期、报价或订单标识、往来上下文及用户填写的说明。相同联系人、相似主题、回复头或模型置信度均不能单独证明项目归属；需要可核对的内容或上下文证据。正文中的指令不作为工具授权。

| 判断结果 | 处理方式 |
| --- | --- |
| 明确属于已有项目 | 自动关联该项目，保存分析来源、依据和版本；人工锁定的归属不覆盖 |
| 新一轮合作/新项目机会 | 在联系人及项目分析结果中展示“新合作机会”，由用户创建或选择项目，不自动并入旧项目 |
| 非项目交流 | 保留在联系人往来中，不进入项目邮件列表、进度摘要或项目通知 |
| 证据不足或多个项目冲突 | 保留未分配/待确认，列出候选及原因，不强制归属 |

公司 A 的李先生可同时参与德国、美国展会及下一年度项目：

| 邮件情形 | 目标结果 |
| --- | --- |
| 明确讨论德国展会的设计、报价或交付 | 进入德国项目，不进入美国项目摘要 |
| 明确讨论美国展会；即使主题仍为旧德国线程 | 按当前内容判断，不盲目继承德国项目；有人工归属冲突则待检查 |
| “圣诞快乐，祝你假期愉快” | 仅显示在联系人往来中 |
| “圣诞快乐，另外德国展位设计已确认” | 问候不妨碍识别有效项目内容，归属德国项目并总结确认事项 |
| “明年德国展会还找你们合作” | 若是独立的新一届合作，展示新合作机会；已有明年项目且证据明确时归入明年项目 |
| 原项目的交付、账款或售后延续到明年 | 仍可归原项目，不能仅按年份切分 |
| 内容只有“好的，谢谢” | 有明确上下文才能判断是否为项目确认；纯礼貌不新增进度事实 |
| 李先生新发邮件，没有可确认的项目线索 | 联系人详情可见，项目归属待确认 |
| 邮件涉及项目中多位联系人 | 项目邮件列表只展示一次，各联系人详情可分别显示其参与关系 |

同一封邮件实质涉及多个项目时，暂不自动选定单一主项目，交由用户确认；不能为了满足现有单一 projectId 丢掉冲突。逐封分析，不把一个线程的整段历史一起迁移。RFC 线程关系作为重要上下文，但邮件内容转向新项目、问候或新合作时需要重新判断。

### 6.3 进度总结

AI 总结默认包括：项目目前在做什么、已确认事项、最新变化、未解决问题、双方各自待办/等待事项、下一步及有证据的日期。每个重要结论应能回到对应邮件；无证据的日期、任务完成、合同确认或百分比不能补写。

摘要属于可更新的派生视图，可以在用户发起分析或合格新邮件处理后自动保存版本。用户已修改的摘要不得被自动覆盖，应显示新的建议版本供选择。自动摘要不等于自动应用任务、需求、决策等业务事实；这些继续遵守已有 Schema 校验、人工覆盖和应用规则。

分析失败或只完成部分邮件时，显示未完成数量及摘要覆盖范围，不把部分结果写成完整结论。复用邮件输入及项目上下文版本，重复点击不会产生重复记录；新结果不能覆盖基于更新输入的摘要。人工移动归属后，原项目及目标项目摘要均需刷新或标为待更新。

### 6.4 新来信处理与 OpenClaw 通知

执行顺序：正常同步并保留原始邮件 → 现有发件规则及真人/机器分类 → 匹配手动联系人及候选项目 → 内置 AI 判断本封归属 → 校验并保存关联 → 更新项目派生摘要 → 生成符合条件的持久化通知事件 → OpenClaw 领取并发送。

摘要更新可单独重试，其失败不阻断已确认相关邮件的通知。归属未确定时先显示待确认，不凭猜测发出“项目新邮件”通知。用户确认后，仅符合新来信通知范围的邮件可触发一次通知；历史批次始终静默。

| 来信结果 | 项目邮件与摘要 | 本需求的项目通知 |
| --- | --- | --- |
| 明确属于进行中项目的真人新来信 | 关联对应项目，更新摘要 | 通知，包括进度更新；是否需要回复作为附加信息 |
| 明确属于已结束项目 | 保留项目归属，摘要可更新但不重开项目 | 静默 |
| 纯节日问候/其他非项目交流 | 仅联系人往来 | 静默 |
| 新一轮合作，尚无对应项目 | 显示新合作机会 | 不冒用旧项目通知；可按独立的可行动来信规则通知 |
| 归属不确定或冲突 | 待确认，不写入确定摘要 | 确认前静默 |
| 用户主动分析历史、历史补拉或其恢复任务 | 可归类和总结，保留历史标志 | 静默，不补发旧通知 |
| 本方已发邮件 | 可归类并更新项目摘要 | 不通知自己的发信 |
| 自动回复、退信、回执或其他机器邮件 | 可保留有证据的资料，不推进项目进度 | 不触发项目通知 |

实现契约：进行中项目的合格实时真人新来信以独立 `active_project_update` 原因通知；不需回复/行动也不允许 Agent 用 `result.actionable=false` 否决。后端在完成事件时重验项目状态、成员上下文与邮件版本；历史、已发、机器、黑名单、已结束项目和过期上下文不走此分支。事件、Skill 和 OpenClaw 模板已同步；运行时 Gateway 重配、通知投递与真实反例尚待本轮验收。

现有黑名单与机器邮件静默限制继续优先。用户设置的白名单强制通知及普通可行动通知是独立规则，需在页面说明命中原因：非项目邮件未触发项目通知，不代表它不能通过用户另设的白名单或可行动规则通知。已结束项目也只关闭本需求的项目通知渠道，不隐式修改用户其他通知设置。

同一封邮件若同时命中项目、白名单和可行动规则，合并为一次通知，并展示相应原因。通知包含公司、项目、联系人、本封内容概要、是否需要回复/行动及邮件入口。OpenClaw 不再自行猜测已校验的项目归属，也不能把“无需行动”直接否决成“无需通知”；明确项目通知条件须由服务端控制。

通知通过现有持久化事件和 outbox 发送，保留幂等、重试和结果确认。OpenClaw 离线时同步及分析继续，恢复后按策略处理积压；历史分析不能产生积压通知。项目在任务执行期间被结束或成员/人工归属发生改变时，写入结果及投递前重新检查当前版本和状态，防止旧任务错误归类或在结束后继续推送。

### 6.5 正文、线程与原始证据

邮件详情继续只显示本封当前正文；历史往来通过上一封/下一封查看。线程导航和项目邮件列表是两种视图：前者展示真实回复关系，后者只列本项目归属，不能因为导航到其他邮件就自动改变项目。

分析当前正文为主，必要时显式携带已存储的历史上下文；不能把引用的旧邮件再次当成本封新增决定，也不能因移除引用而丢失“好的”所需的关联背景。

原始 MIME、完整文本/HTML 和来源证据保留。人工移动邮件或线程归属应记录操作者、操作 ID、前后值，并使受影响项目摘要标为待更新；不把旧摘要文字当作新项目的已确认事实。

## 7. 当前数据与接口契约

以下为实现后的共享契约；具体请求/错误/分页细节以专题为准。此处记录接口事实，不作为运行或部署通过的证明。

| 部分 | 当前实现与契约 |
| --- | --- |
| 联系人 | `Contact.notes`、`ContactEmail[]` 多邮箱及主邮箱；`GET/PATCH /mail/crm/contacts/:contactId`；普通列表限 confirmed，可按 `companyId` 精确筛选 |
| 公司 | `Company.website/address/notes`、显式 `contactIds` 成员；`GET/PATCH /mail/crm/companies/:companyId`；公司至少保留一名 confirmed 联系人 |
| 项目成员/状态 | `ProjectContact(projectId,contactId,isPrimary)`；新建需公司与至少一名公司联系人；`status=active|completed` 与 stage 保持完成态一致 |
| 联系人邮件 | `/mail/crm/contacts/:contactId/messages` 按所有已登记邮箱和实际 From/To/Cc/Bcc 匹配，返回参与角色、逻辑去重和分页 |
| 项目邮件及归属 | `GET /mail/projects/:projectId/messages` 分页；邮件人工归属通过 `PATCH /mail/messages/by-id/:messageId/project` 携带 expectedVersion/operationId，null 为人工锁定“无项目” |
| 项目分析 | `/mail/projects/:projectId/analysis` 创建/读取 latest，`/mail/project-analysis/:jobId` 读取 job/items，附 cancel/retry；日期两端按业务时区包含，limit 最大 500 |
| 摘要与通知 | 摘要附来源/覆盖/过期；人工摘要受保护并可由用户显式采用建议；项目通知走经服务端重验的 `active_project_update` 分支 |
| 工具适配 | CLI/MCP 共用 `scripts/tool-contracts.mjs` schemas/runtime validator 和后端业务 API；工具可用不构成 Agent 创建/修改 CRM 记录的授权 |

新增或变更数据字段/关系才创建 Prisma Migration。沿用 PostgreSQL、NestJS 模块化单体，不引入独立 CRM 服务或另一个数据库。

用户字段校验、邮箱唯一性、关系一致性、operationId 幂等、版本冲突和并发保护在业务服务完成，不能只靠页面禁用按钮。公司成员变化不会触发旧邮件重通知；模型和外部 Agent 不直接访问数据库。

模型返回的项目 ID 必须属于服务端提供的候选及用户可访问范围；归属、证据引用和输入版本校验后才能写入。AI 失败不阻断收邮件，任务留待恢复，不回退成“只有一个项目就全部归类”。大批历史使用分批处理和已有摘要作上下文，不把整个邮箱一次塞进提示词。

## 8. 现有自动联系人及复核的迁移

用户不需要自动联系人，但现有记录可能已被手工确认、编辑、合并或用于业务事实。**不能简单删除所有 provisional 或清空联系人表。**

已实现旧记录清理的只读预览、审计退档和可审计恢复 API。它们不会在应用启动时自动执行，且未在生产数据上执行；真实清理前仍需备份、审核预览，回滚只针对对应的操作 ID。隔离 PostgreSQL 回归覆盖纯自动旧联系人退档和恢复。对生产遗留记录进行任何整理时仍须按以下流程：

1. 先停止所有自动创建入口，保证后续同步及对账不会再次产生自动联系人。
2. 备份后生成只读清单，区分用户创建/确认/修改的联系人、纯自动且无业务依赖的记录、来源不明或有依赖的记录。
3. 用户维护过的资料保留。纯自动记录从正常通讯录退出，关联的“联系人待确认”复核不再占据常规待办，保留处理原因和审计。
4. 有业务来源、合并关系或人工修改的旧记录，不自动删除；保留可追溯历史并列入待整理清单。纯自动、无依赖记录如需物理删除，另提供具体清单和可恢复处理方案。
5. 重新匹配保留的手动联系人与历史邮件，验证联系人详情完整；此过程不修改邮件正文、不重复创建业务事实、不重发通知。

不影响分类冲突、任务分析等其他有效复核。公司与项目的既有人工资料也保留，不通过域名重新分配。数据清理结果分别说明保留、退出正常列表、解除关联和实际删除数量。

## 9. 文档采用的默认规则

用户明确要求的目标已经记录；以下是为使需求可执行而采用的建议默认值，尚未声称用户逐项决定：

- 一个联系人可暂不属于公司，默认至多属于一个公司；一家公司有多个联系人和项目。
- 一个新项目属于一个公司、包含多个该公司的对接联系人；多公司联合项目和第三方参与者管理不在此次范围。
- 一封邮件默认只有一个当前主项目，沿用现有 projectId；同时属于多个项目的多对多邮件归属需另行定义。
- 官网、地址、备注手动填写；不自动抓取网站或从签名填资料。
- 内置 AI 可自动归类证据明确的项目往来；单项目仍排除非项目交流及新一轮合作。模糊归属交由用户确认，人工修正优先。
- 分析按钮执行可见范围内的历史归类和派生摘要更新；后续新邮件增量处理。历史批次不通知，不默认分析整个邮箱。
- 派生摘要自动保存版本，人工编辑保留；业务事实写入继续沿用已有应用规则，AI 不自动创建 CRM 实体或结束项目。
- 项目状态由用户设置；进行中项目的已确认相关真人新来信通知 OpenClaw，已结束项目的项目通知静默。独立白名单/可行动规则按 6.4 执行。

实施时如改变这些默认规则，先更新本文及验收，不默默扩大范围。

## 10. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| C1 | 未登记邮箱来信 | 邮件正常同步和分类，没有新增联系人或联系人确认复核 |
| C2 | 初始补拉、增量、对账、失败重试、重启恢复 | 均不自动创建联系人，也不复活已退出列表的自动记录 |
| C3 | 手动添加联系人 | 保存后直接可用，精确邮箱匹配已有历史及后续收发邮件 |
| C4 | 多邮箱、CC 和多位联系人 | 详情显示参与方式，匹配完整，副本与多参与人不造成重复邮件 |
| C5 | 重复邮箱和并发保存 | 明确冲突；同 operationId 重放不重复建联系人 |
| C6 | 同域名不同联系人 | 未经选择，不自动加入公司、项目或合并身份 |
| O1 | 创建/编辑公司 | 可选择多个联系人，保存官网、地址、备注；无自动资料写入 |
| O2 | 点击公司 | 显示资料、联系人和项目，成员/项目入口可用 |
| O3 | 调整成员 | 不删除联系人、邮件或证据；对既有项目冲突有明确提示 |
| P1 | 同公司创建德国、美国两个项目 | 分别选择对接人，项目独立；同一联系人可参与二者 |
| P2 | 已确定项目线程的新回复与已发副本 | 内容及上下文支持原归属时自动进入对应项目；线程内容转向其他业务时重新判断 |
| P3 | 同一联系人多项目、新主题、缺失回复头或归属冲突 | 比较候选项目并核对内容，不把全部联系人邮件塞入一个项目；不确定邮件待确认 |
| P4 | 人工修正项目归属 | 记录审计，保护人工设置，受影响摘要提示待更新 |
| P5 | 项目总结与进展 | 只使用本项目来源；无摘要时显示空状态，不臆造进度或由自动回复推进 |
| A1 | 一个项目与纯节日问候 | 问候不归项目、不触发项目通知；正常项目邮件可自动归类 |
| A2 | 同一联系人、同主题的德国/美国项目 | 按内容和上下文分开，摘要无跨项目污染，冲突留待确认 |
| A3 | 今年合作结束、确认明年合作 | 没有明年项目时展示新合作机会；不自动建项目、不并入今年项目；跨年交付仍可留原项目 |
| A4 | 点击分析历史 | 可见范围、进度与部分失败；归类和摘要可追溯，没有补发通知 |
| A5 | 进行中项目相关新来信 | 归属明确才触发一次 OpenClaw 通知；纯进度更新也支持；已发副本/机器邮件不触发 |
| A6 | 已结束项目收到相关来信 | 保留归属、不重开项目、不产生项目通知；其他独立规则命中原因清楚 |
| A7 | 同时命中项目、白名单及可行动规则 | 合并一次通知，不重复投递，不被 Agent 的非行动判断错误取消 |
| A8 | 重复点击、AI 失败、服务重启、OpenClaw 离线 | 幂等写入，任务可恢复，收件不中断；显示未完成范围，不猜测归属或重复事实 |
| A9 | 运行中人工修正/结束项目，旧分析迟到 | 校验最新状态及版本，保护人工归属和摘要，不用旧结果覆盖或继续推送 |
| A10 | 问候夹带项目确认、引用历史、无信息短回复 | 识别本封有效业务内容，使用必要上下文；不把旧引用当新决定或纯礼貌当进展 |
| M1 | 旧自动联系人整理 | 保留人工维护与依赖数据，不清空邮件；过程可预览、可追溯、可恢复 |
| M2 | 历史关系匹配 | 无重复业务事实或通知，邮件数量及原始证据不因 CRM 整理减少 |
| U1 | 邮件详情、桌面/手机及所有适配入口 | 当前正文与前后导航继续可用；分页、权限、错误和关系规则一致 |

建议交付顺序：停止自动创建并制定旧数据整理方案 → 手动联系人与往来 → 公司资料/成员/详情 → 项目对接人、状态及人工分配 → 历史 AI 归类和摘要 → 新来信增量分析与 OpenClaw 通知 → 全链路验收。
